# 2.8 Configurar hr-zuul-server

`@EnableZuulProxy` na classe principal liga o proxy do Zuul: é ele que lê as rotas do `application.properties` e faz o encaminhamento das requisições. `@EnableEurekaClient` registra o gateway no Eureka, mesmo padrão do hr-worker e do hr-payroll, e é o que permite as rotas apontarem pro nome do serviço em vez de host e porta fixos.

`spring.application.name=hr-api-gateway-zuul` é o nome com que o gateway se registra no Eureka. `server.port=8765` fixa a porta do gateway: diferente do hr-worker, que sobe em porta aleatória, essa porta precisa ser conhecida, porque o gateway passa a ser o único endereço que o cliente chama. `eureka.client.service-url.defaultZone=http://localhost:8761/eureka` aponta pro hr-eureka-server, igual nos outros módulos.

As rotas são declaradas em pares:

```properties
zuul.routes.worker.service-id=hr-worker
zuul.routes.worker.path=/hr-worker/**

zuul.routes.payroll.service-id=hr-payroll
zuul.routes.payroll.path=/hr-payroll/**
```

`path` é o prefixo que o cliente chama no gateway e `service-id` é o nome registrado no Eureka pro qual a requisição é encaminhada. O `worker` e o `payroll` no meio da chave são só ids arbitrários da rota, servem pra amarrar o `path` e o `service-id` de uma mesma rota.

O prefixo do `path` é removido antes do repasse: `localhost:8765/hr-payroll/payments/1/days/5` chega no hr-payroll como `/payments/1/days/5`, e `localhost:8765/hr-worker/workers/1` chega no hr-worker como `/workers/1`.

Usar `service-id` em vez de uma `url` fixa é o que mantém Eureka e Ribbon no caminho: o gateway resolve o endereço pelo nome do serviço e balanceia a carga entre as instâncias do hr-worker, que sobem em porta aleatória e não teriam endereço fixo pra ser configurado aqui.

---

#### English

`@EnableZuulProxy` on the main class turns on the Zuul proxy: it is what reads the routes from `application.properties` and forwards the requests. `@EnableEurekaClient` registers the gateway with Eureka, the same pattern as hr-worker and hr-payroll, and is what allows the routes to point to the service name instead of a fixed host and port.

`spring.application.name=hr-api-gateway-zuul` is the name the gateway registers with in Eureka. `server.port=8765` pins the gateway's port: unlike hr-worker, which starts on a random port, this port has to be known, because the gateway becomes the only address the client calls. `eureka.client.service-url.defaultZone=http://localhost:8761/eureka` points to hr-eureka-server, same as the other modules.

Routes are declared in pairs:

```properties
zuul.routes.worker.service-id=hr-worker
zuul.routes.worker.path=/hr-worker/**

zuul.routes.payroll.service-id=hr-payroll
zuul.routes.payroll.path=/hr-payroll/**
```

`path` is the prefix the client calls on the gateway and `service-id` is the name registered in Eureka the request is forwarded to. The `worker` and `payroll` in the middle of the key are just arbitrary route ids, they only tie together the `path` and the `service-id` of the same route.

The `path` prefix is stripped before forwarding: `localhost:8765/hr-payroll/payments/1/days/5` reaches hr-payroll as `/payments/1/days/5`, and `localhost:8765/hr-worker/workers/1` reaches hr-worker as `/workers/1`.

Using `service-id` instead of a fixed `url` is what keeps Eureka and Ribbon in the path: the gateway resolves the address by the service name and load balances between the hr-worker instances, which start on a random port and would have no fixed address to configure here.
